Getting started

NoaCG Studio makes broadcast graphics in the browser: lower thirds, scoreboards, tickers, quiz boards, countdowns. There are two ways to get them on air. One is a live production you drive from an online dashboard. The other is an exported package that runs offline in whatever system your studio already uses.

  1. Open the studio. The creation wizard has four doors: a template from the catalog, a description for AI, your own artwork, or a blank start.
  2. Set the colors, typefaces, logo and motion beside a live preview. Every change writes real HTML, CSS and JavaScript. You can open it, or never look at it.
  3. Finish, then either export a package straight away, or collect graphics into a production and run the show.

The guides below cover the rest: bringing your own design in as an SVG, connecting playout systems, live data, and letting a coding agent do the authoring.

Import your own SVG graphic

SVG import is how you bring a graphic you designed yourself into NoaCG. Design it in Illustrator, Figma or Inkscape, export an SVG, and drop it on the Import door. Your text layers become operator fields. The drawing itself is not redrawn: your typography and your geometry go on air as they are, and export to every target like any other graphic.

Where to drop it: the studio → New graphic → Import graphic.

The five rules that decide whether it works

  1. Give the file a size. A viewBox (or width+height) is required. It is the design space every field position is measured against. 1920×1080 with a transparent background is the predictable choice for frame-exact artwork. A smaller artboard imports as a free-floating object placed by the zone picker.
  2. Keep text as text. Every live <text> layer becomes an editable operator field, bound in place. Text converted to outlines cannot be edited in place. The import offers a fallback, a matching editable line placed over the measured outline, but re-exporting with real text gives a better result.
  3. Name your layers. Layer names become the field labels an operator reads. "Home team" reads better than "Rectangle_3". No naming convention is required beyond that.
  4. Embed your pictures. A linked image is a network reference and is stripped on import, because an exported graphic has to play out with no internet.
  5. Do not animate in the design app. SVG-native (SMIL) animation is removed with a note. Motion is added in NoaCG's Animation step, where the timeline and the playout server can drive it deterministically.

When a typed value is longer than the design was drawn for, the generated code answers in one fixed order: fill the shape you drew the line in, grow the panel only if you opted in, wrap into the room the design already has, shrink to a readability floor, then warn the operator. The artwork is not reshaped behind your back, and copy is not cut.

Fonts

An SVG names its fonts. If the playout machine does not have the family, the graphic will not match the design. The import inventories every family and, per family, matches a bundled face, offers the Google Fonts library (fetched at design time and embedded, so exported code never reaches the network), or takes a font file you upload for a licensed face. An unresolved family warns and continues. PostScript names (Archivo-Bold) are understood.

Export settings, app by app

AppSettings that matter
IllustratorFile → Export → Export As… → SVG (not "Save As"). Font: SVG (not outlines) · Images: Embed · Object IDs: Layer Names · Minify: off. Name your layers first; duplicates are safe.
FigmaName the layers, select the frame, Export → SVG with Include "id" attribute ON and Outline text OFF.
InkscapeSave As… → Plain SVG. Label layers and objects. Do not run Object to Path on editable text, and do not use flowed text (drag-drawn text boxes): it exports as <flowRoot>, which no browser renders.

Ready-made files to try are in the repository's docs/svg-samples folder: a lower third, a scorebug, an outlined-text example and an Illustrator-shaped export.

A quiz board can carry its behaviour in the file too. Draw the base look, then one hidden layer per moment (answer picked, right, wrong, locked in), and the import's behaviour pickers wire them up. See graphics with behaviour.

End credits

A credit roll is a list of people, and a list of people is not a list of fields. Every end-credits design has one field for the whole roll: a text box you paste into, in the studio, on the production dashboard, or later in whatever plays it out. A show with five camera operators does not add five fields to the template.

So the format has to carry the one distinction a credit roll is made of: which part is the role, and which part is the person. There is one mark to learn.

A colon ends a role. Everything else is a name.

Director: Alex Rivera

A role with more than one person puts the colon at the end of its own line, and the people follow beneath it, for as long as no new role appears: 

Camera Operators:
Jonas Berg
Lena Fors
Petri Salo

You type it the way you would write it on paper, instead of repeating the word Camera on five lines.

The complete set

  • Director: marks a role. Every line under it is one of its names.
  • Director: Alex Rivera is the same, inline, for a role with one person.
  • Director TAB Alex Rivera is the same. This is what a paste from a Google Doc table or a spreadsheet column looks like.
  • Director | Alex Rivera is the same, with the older separator. Existing lists keep working.
  • Alex Rivera is a name. It joins the role above it, or stands on its own if there is none.
  • # PRODUCTION is a department heading, above a run of roles.
  • A blank line starts a new section.

A semicolon works everywhere a colon does, because that is the mark some other template systems use.

Nothing is required. Paste a bare list with no marks at all and every line is read as a name, which gives a clean column of names. A heading is marked or it is not a heading, which is what lets a roll end on "Special thanks to everyone who made this show possible" without that sentence being set in accent capitals.

The same text in any design

The format says what the content is, never how it is arranged, so switching design does not mean retyping the credits. Classic Roll gives centred blocks with the role over its names. Column Roll puts the role right-aligned in a left column with its names stacked in the right. Programme Roll sets it as serif leader rows on paper. Walls, donor boards, sponsor crawls and schedules in the same category read the same text.

Classic Roll adds one choice in the wizard's Style step, Emphasis. Role (the default) sets the role big and bold with its names quieter beneath it, which is what stays right when one role credits five people. Name sets the name big with the role as a small label above it: the film convention, and the better read when nearly every role has exactly one person.

OBS, vMix & any browser source

A published production gives you one output URL, …/output?production=<slug>, that renders the whole show: transparent, all its graphics, driven live from the playout dashboard. Anything that can show a web page can carry it. Load it once and leave it up. Graphics are cued by the operator, not by reloading the source.

Four rules apply to every browser-based playout:

  • Transparency is built in. Do not set a chroma key. A black or white box behind the graphic means the host is forcing an opaque background. Check its custom-CSS and background settings.
  • Match the resolution exactly. Graphics are designed in real pixels (1920×1080 unless you chose otherwise). A mismatch does not crop, it scales, and scaled text is softer than text rendered at its own size.
  • Resize the source, never the resulting layer.
  • Set the source's FPS to the channel's. Motion is authored in seconds and plays correctly at any rate, but a 30 fps source in a 50 Hz channel judders in a way that looks like the graphic's fault.

OBS Studio

  1. Sources → + → Browser.
  2. Paste the production's output URL. For an exported overlay, tick Local file instead and pick the .html.
  3. Set Width and Height to the graphic's own resolution, and FPS to your channel's.
  4. Leave the background alone. The page is already transparent.

Leave "Shutdown source when not visible" off for a production output. It tears the page down every time you hide the scene, and forces a full rebuild on the way back.

An exported overlay package ships a local relay and launcher (Start controller.cmd on Windows, start-controller.command on macOS, ./start-controller.sh on Linux). It serves the folder locally, opens the operator page, and relays every command into the graphic, which is the route into a page loaded by OBS's or vMix's own browser engine. It works offline and installs nothing.

vMix

  1. Add Input → More → Web Browser.
  2. URL: the output URL, or the full local path to an exported file.
  3. Set the width and height to the graphic's resolution.
  4. Use it as an overlay channel input.

CasparCG

CasparCG plays web pages through its HTML producer, so both routes work: the live output URL for a whole production, or an exported single-file template played from disk with no network at all.

Playing the production's output URL

CG 1-20 ADD 1 "https://noacg.studio/output?production=<slug>" 1
  • 1-20 is channel 1, layer 20. Use whatever your rundown expects.
  • The URL is a capability: anyone holding it can render the production, though not operate it. Treat it like a password.
  • Load it once at the start and leave it up. Graphics are cued from the dashboard, not by re-adding the layer.
  • Add &debug=1 while setting up for an on-screen status readout, and take it off before air.
  • The page recovers by itself after a network drop or a layer restart, rebuilding what was on air without replaying animations.

Letting NoaCG load the layer for you

Instead of typing the command into the CasparCG Client, the production page can send it. Settings → Playout holds one server for the whole studio (host, AMCP port, channel, layer), and the production page grows a Put on air / Take off row. One thing has to run on the machine you operate from, because a browser cannot open a raw TCP socket and AMCP is one: 

npx @noacg/cli caspar agent

Leave that terminal open. It prints an address and token to paste into the Playout settings, listens on 127.0.0.1 only, and CasparCG itself can be any machine on the studio LAN, exactly as with the Client. Test connection round-trips a real AMCP VERSION and shows the server's own version string. On the hosted studio, Chrome asks once whether the site may reach your local network; answer the prompt and it sticks. Safari refuses this outright, so there, use the terminal route: 

npx @noacg/cli caspar play --url "https://noacg.studio/output?production=<slug>" --channel 1 --layer 20

What has been verified The output URL route has run on real hardware: a CasparCG 2.3.2 server rendered it at 1920×1080, transparent, surviving a renderer restart. The one-button connection is newer. Its AMCP wire and every failure state are verified against protocol-accurate fakes and the test suite, but it has not yet driven a real CasparCG server. If it misbehaves on yours, the manual command above is the same live link, and we would like to hear about it.

Playing an exported file

Export with the CasparCG target and you get one self-contained .html, with fonts and images inlined and no network needed. Drop it into the server's template folder and drive it as a normal HTML template: 

CG 1-20 ADD 1 "<template-name>" 1 "<templateData>…</templateData>"
CG 1-20 PLAY
CG 1-20 NEXT
CG 1-20 STOP

A CasparCG client sends values by field id (f0, f1, …), so every exported package ships FIELDS.md: each field's id, name, type and default, with paste-ready payloads built from that graphic's own ids. Keep it open beside the client.

The playout dashboard

A production is the live unit: a pool of graphics, a cue rundown prepared in advance, and one persistent output URL. Each graphic is its own layer, so a bug, a lower third and a ticker can be on air at once. Publish the production and the dashboard drives it from anywhere: another tab, an OBS dock, a phone at the desk.

  • Preview and program. Two monitors and the verbs an operator uses: select a cue, check it on preview, Take. Staged edits air on an explicit take, never mid-keystroke.
  • Rehearse vs Show. Rehearse drives a local copy, so you can walk the rundown without touching the air. Show drives the published output. The mode strip on the production page says which you are in.
  • Recovery is built in. Every command is a row in a durable log. The on-air renderer applies rows in order and, after a network drop or restart, catches up in order, rebuilding what was on air without replaying animations on screen.
  • Pictures without templates. "＋ Add pictures…" turns image files into cues, such as a holding slide or a sponsor card, aired like any other cue. There is one picture layer per production, so stills replace rather than stack.

Audience join pages

A production can invite its audience in. A public join page at a readable URL (noacg.studio/join/<name>, the kind you read out on air) collects viewer messages and votes from any phone, with no app and no account.

  • Nothing viewer-written airs on its own. Send-ins land in a moderation inbox, and an operator picks what goes into the graphic. That separation is structural, not a setting.
  • Votes tally live into poll graphics. Open the vote, close it, put the result on air when you are ready.
  • A presenter view (a separate link) shows the host what is coming without giving them operator controls.

Graphics with behaviour

A lower third plays and stops. A quiz board has to know which answer the contestant locked in and whether it has been revealed yet. NoaCG graphics can carry that logic themselves, as named states and real operator events, and the control panel is generated from them, so a move that would be wrong is greyed out instead of being wrong.

  • A quiz runs Select answer, Lock it in, Reveal. Each one is a button on the dashboard, and each is legal only when the board's state allows it.
  • A scoreboard carries score up/down and clock start/stop as events. The numbers are data an operator or a feed writes.
  • Data never causes a state change. Updating a name or a score re-renders fields. States move only on operator events, which is what makes a feed safe to leave running.
  • Everything still degrades to plain stepping. Hand the same graphic to any playout system and it walks its steps in order like an ordinary template. The extra buttons are what you get when you drive it from NoaCG, not a reason it will not play elsewhere.

You can author behaviour without code. An imported SVG quiz board is layers: draw each moment (answer picked, right, wrong, locked in), hide those layers in the design app, and the import wires them to the quiz behaviour. See the SVG guide.

Live data

Three doors, from no setup to fully automated. All of them follow the same rule: data updates change what a graphic shows, never what state it is in. The operator always wins, because their command lands later in the same log.

Type it on the dashboard

Every field is editable live from the production page: edit, stage, take. For most shows this is the whole answer.

A Google Sheet (or any published CSV)

Point a graphic at a published sheet and its fields follow the sheet, from anywhere, by anyone you share the sheet with. In the sheet: File → Share → Publish to web → CSV. In the studio, add the live-data source and paste the link. The generated polling code is ordinary, commented JavaScript appended to the graphic's own code, with column headers mapped to field titles. It runs wherever the graphic runs: the preview, an OBS browser source, an exported package. You can open and edit the mapping like anything else.

The Production Data API

For a timing system, a results service or your own scripts: push values into a published production over plain HTTPS, authenticated by the production's own data key (minted when it is published). Writes become rows in the production's command log, so the renderer cannot tell your update from an operator's. 

curl -s https://noacg.studio/api/data/update \
  -H "Authorization: Bearer $NOACG_DATA_KEY" \
  -H "Content-Type: application/json" \
  -d '{"graphic": "House Scorebug", "values": {"Score A": 2, "Clock": "43:12"}}'
  • Fields are addressed by the labels the graphic shows its operator ("Score A"), so a feed and a spreadsheet speak the same language.
  • The key can write data only. It cannot play, stop, take or clear anything. A feed that could clear the frame would be a second operator with no face.
  • PATCH /api/data/patch goes one step further: write to a data path (match.home.score) and every graphic bound to it follows, without the feed knowing the rundown.
  • A worked example ships in the repository: a weather mini-pack driven by a small Node connector polling Open-Meteo. The full reference, limits and error shapes are in DATA_API.md.

Make graphics with Claude Code, Codex or any coding agent

A coding agent can write the HTML, CSS and JavaScript of a graphic. What it cannot work out on its own is what NoaCG requires of one: which fields the operator sees, which events it accepts, and whether it still behaves under a real playout run. The noacg command-line tool supplies that part. It carries the contract, runs the same validator the studio runs, and can put the finished graphic in your library.

Install

One command. It registers the noacg MCP server with Claude Code, and fetches the tool the first time an agent uses it: 

claude mcp add noacg -- npx -y @noacg/cli mcp

You need Node.js 20 or newer, and a system Chrome or Edge, which the validator drives in headless mode. No account is needed until you want to save a graphic into a library.

To type the commands yourself, install the tool once:

npm i -g @noacg/cli

That gives you noacg. Every command below also works as npx @noacg/cli <command> with nothing installed. The package is @noacg/cli on npm.

Other agents

Codex. The same server, its own command:

codex mcp add noacg -- npx -y @noacg/cli mcp

Any other MCP client. Run the server over stdio. It exposes types, scaffold, validate, inspect, screenshot, save and the contract references as tools: 

npx -y @noacg/cli mcp

No agent, just you. Every verb is a plain command. See the loop below.

By default everything talks to https://noacg.studio. Set NOACG_URL to point at a self-hosted or local deployment instead.

The loop

Ask your agent for a graphic ("make me a clean scoreboard for a floorball stream: home, away, period, clock"), or walk it yourself.

  1. Start from a working chassis. This step is optional, because an agent can also author from scratch against the contract. 
    npx @noacg/cli scaffold --type scoreboard --design neutral --out my-scorebug
  2. Author it. Edit the package's HTML, CSS and JavaScript the way you normally work.
  3. Validate. This is the studio's own gate plus a live playout bench, with off-air, on-air and stress screenshots, so the agent can see what it made. 
    npx @noacg/cli validate my-scorebug --screenshots shots
  4. Log in, once per machine. The key can only create graphics. 
    npx @noacg/cli login
  5. Put it in your NoaCG library. 
    npx @noacg/cli save my-scorebug

validate reports findings the way a compiler reports errors, and the agent iterates until it is clean. save refuses anything that does not pass. The saved graphic opens in your library like any other: editable in the studio, exportable to every target, ready for a production.

The package on disk is at the same time a valid SPX package and an EBU OGraf v1 graphic. Zip it and it also imports through the studio's Import door, or plays in any OGraf renderer. The full reference is AGENT_CLI.md.
