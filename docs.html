Getting started

NoaCG Studio makes broadcast graphics in the browser: lower thirds, scoreboards, tickers, quiz boards, countdowns. There are two ways to get them on air. One is a live production you drive from an online dashboard. The other is an exported package that runs offline in whatever system your studio already uses.

  1. Open the studio. The creation wizard offers four starting points: a template from the catalog, a description for AI, your own artwork, or a blank start.
  2. Set the colors, typefaces, logo and motion beside a live preview. Every change writes real HTML, CSS and JavaScript. You can open it, or never look at it.
  3. Finish, then either export a package straight away, or collect graphics into a production and run the show.

The guides below cover the rest: what each kind of graphic asks you to type, bringing your own design in as an SVG, connecting playout systems, live data, and letting a coding agent do the authoring.

Graphics

Every graphic is one kind in one design. The kind decides what you type and what the operator's buttons do. The design decides how it looks. Changing the design never means retyping the content.

Most kinds need no guide: a lower third, a card, a corner bug or a countdown takes a few plain fields and the wizard shows you all of them at once. The four below are worth reading first, because each asks for its content in a particular shape.

  • Scoreboards - two teams, two scores, and a goal press that moves one of them.
  • Quizzes and game shows - a question, the answers, a locked-in pick and the reveal.
  • End credits - the whole roll in one text box.
  • Tickers - the whole rundown in one text box.

Scoreboards

A scoreboard has four fields: Team A, Score A, Team B and Score B. Type a new score and the number on air changes. Nothing else moves, and nothing has to be played again.

The goal press moves the score

The operator's buttons are Goal A, Goal B, Clear flag and Full time. Goal A raises the goal marker and adds one to Score A on the same press, so there is nothing else to remember while the marker is up. Press it again while the marker is still up and it plays again and adds another. Clear flag takes the marker down and leaves the score where it is.

Full time marks the result final. It is independent of the goal marker, so a goal and a full-time call cannot get in each other's way.

Any figure can still be typed. The score is a value, not a mode, which is why correcting one after the fact is only a number changing on screen.

The designs

Match Strip is the sport strip: team names against big scores with one accent edge. Quiet Score is a panel-free corner stack, two rows split by a hairline. House Score and Frost Score are the house and frosted-glass versions. All four take the same fields and the same buttons.

Quizzes and game shows

This is the kind a school or student production runs: a question on screen, a contestant picks, the pick is locked, the correct answer is revealed. There are three boards, for two, three and four answers, and they behave identically. More rows means more fields, never more buttons.

What you type

The Question, then Answer A to Answer D (fewer on the smaller boards). Two more fields belong to the operator rather than the audience: Correct answer, set before the show, and Selected answer, set as the contestant makes their pick. Typing in either one changes nothing on screen by itself.

Running it

  1. Select answer highlights the pick. Press it again with a different letter as often as the contestant changes their mind.
  2. Lock it in makes the pick final. Select then greys out, and it is not merely refused: the board has no route out of locked except the reveal, so a late selection has nowhere to go.
  3. Reveal correct shows the right answer, and marks the pick and the correct answer differently when they are not the same row.
  4. Show audience result is optional and comes after the verdict. It paints a percentage on every row, read from one field written in row order: 34 | 52 | 9 | 5.

Locking a pick nobody has seen yet

A game show usually locks the answer before showing it. Type the letter into Selected answer without pressing Select, then press Lock it in straight from the question: the board locks with the choice still hidden. Reveal choice then shows it as its own beat. Going straight to Reveal correct from there is allowed too, because the verdict shows the pick anyway.

In a playout system that has no buttons

The board's default path is question, reveal, out. A playout system that only knows how to step forward gets exactly that, with no control page and nothing to configure.

The designs

Arena Quiz is the game-show board: a leaning question slab over four lettered answer rows. House Quiz, Frost Quiz and Clean Quiz are the house, frosted and quiet versions of it. The two-answer and three-answer boards carry four matching designs each, named Split and Triple.

End credits

A credit roll is a list of people, and a list of people is not a list of fields. Every end-credits design has one field for the whole roll: a text box you paste into, in the studio, on the production dashboard, or later in whatever plays it out. A show with five camera operators does not add five fields to the template.

So the format has to carry the one distinction a credit roll is made of: which part is the role, and which part is the person. There is one mark to learn.

A colon ends a role. Everything else is a name.

Director: Alex Rivera

A role with more than one person puts the colon at the end of its own line, and the people follow beneath it, for as long as no new role appears: 

Camera Operators:
Jonas Berg
Lena Fors
Petri Salo

You type it the way you would write it on paper, instead of repeating the word Camera on five lines.

The marks

  • Director: marks a role. Every line under it is one of its names.
  • Director: Alex Rivera is the same, inline, for a role with one person.
  • Director TAB Alex Rivera is the same. This is what a paste from a Google Doc table or a spreadsheet column looks like.
  • Director | Alex Rivera is the same, with the older separator. Existing lists keep working.
  • Alex Rivera is a name. It joins the role above it, or stands on its own if there is none.
  • # PRODUCTION is a department heading, above a run of roles.
  • A blank line starts a new section.
  • The text before a colon has to be 48 characters or shorter to be read as a role. A longer line is a name, so a sentence that happens to contain a colon is not turned into a job title.

A semicolon works everywhere a colon does, because that is the mark some other template systems use.

Nothing is required. Paste a bare list with no marks at all and every line is read as a name, which gives a clean column of names. A line is never promoted to a heading because of where it sits, so a roll can end on "Special thanks to everyone who made this show possible" without that line being set in accent capitals.

The same text in any design

The format marks roles and names; the design decides the arrangement. Switching design does not mean retyping the credits. Classic Roll gives centred blocks with the role over its names. Column Roll puts the role right-aligned in a left column with its names stacked in the right. Programme Roll sets it as serif leader rows on paper. Walls, donor boards, sponsor crawls and schedules in the same category read the same text.

Classic Roll adds one choice in the wizard's Style step, Emphasis. Role (the default) sets the role big and bold with its names quieter beneath it. Use it when a role credits several people. Name sets the name big with the role as a small label above it: the film convention. Use it when nearly every role has one person.

Tickers

A ticker is a rundown of stories, and a rundown is not a list of fields. Every ticker design has one field for the whole rundown - a text box you type or paste into, in the studio, on the production dashboard, or later in whatever plays it out. Adding a story never adds a field.

So the format carries the one distinction a ticker item is made of: which part is the kicker - the tag a story is filed under - and which part is the story. It is the same shape as the credit roll above, on purpose.

A colon ends a kicker. Everything else is the story.

SPORT: United win 3-0

A desk with several stories puts the colon at the end of its own line, and the stories follow beneath it - until a blank line or the next kicker: 

SPORT:
United win 3-0
City held at home
Rovers sign a goalkeeper

The complete set

  • SPORT: United win 3-0 - one story, tagged SPORT.
  • SPORT: - a kicker; every line under it carries it.
  • SPORT TAB United win 3-0 - the same as the first, which is what a paste from a spreadsheet column gives you.
  • Storm warning issued - a plain story, with no tag at all.
  • A blank line closes the open kicker.

A semicolon works everywhere a colon does. And nothing is required: a rundown typed with no marks at all is a plain list of stories, exactly as tickers read before kickers existed.

Scores, clocks and links are safe

The colon has to be followed by a space, or end the line. That is what keeps a ticker's own numbers out of it: 

NORTHERN UNITED 2:1 CITY ROVERS
Polling stations close at 20:00
Full results at https://example.org

None of those is a kicker, and TRAVEL: the 20:45 service is cancelled is read the way you meant it. One more difference from end credits: a | is not a separator in a ticker, because Bilingual Crawl already splits an item at it into its two languages.

The same rundown in any design

The format says what the content is, never how it is arranged - so switching design never means retyping the rundown. Every ticker draws a kicker in the accent colour ahead of its story, and a design that wants it somewhere else places it itself: Status Rotator puts it in a fixed-width name column, which is what makes a service status scannable.

Import your own SVG graphic

SVG import is how you bring a graphic you designed yourself into NoaCG. Design it in Illustrator, Figma or Inkscape, export an SVG, and drop it on the Import door. Your text layers become operator fields. The drawing is not redrawn. Your typography and geometry go on air as you drew them, and export to every target like any other graphic.

Where to drop it: the studio → New graphic → Import graphic.

The five rules that decide whether it works

  1. Give the file a size. A viewBox (or width+height) is required, and a file with neither is refused. It is the design space every field position is measured against. Use 1920×1080 with a transparent background for full-frame artwork. A smaller artboard imports as a free-floating object, positioned by the wizard's zone picker rather than pinned to exact coordinates.
  2. Keep text as text. Every live <text> layer becomes an editable operator field, bound in place. Text converted to outlines cannot be edited in place. The import offers a fallback: a matching editable line placed over the measured outline. The stand-in is re-rendered type, so the kerning is the font's and not the designer's. Re-export with live text where you can.
  3. Name your layers. Layer names become the field labels an operator reads. "Home team" reads better than "Rectangle_3". No naming convention is required beyond that.
  4. Embed your pictures. A linked image is a network reference and is stripped on import, because an exported graphic has to play out with no internet.
  5. Do not animate or script in the design app. SVG-native (SMIL) animation is removed, as are <script>, on* handlers and <foreignObject>. Every removal is reported on screen. Motion is added in NoaCG's Animation step, where the timeline and the playout server can drive it deterministically.

When a typed value is longer than the design was drawn for, the generated code tries these in fixed order: fill the shape the line was drawn in; grow the panel, if you opted in; wrap into the room the design already has; shrink to a readability floor; warn the operator. It does not reshape the artwork and it does not cut text.

Fonts

An SVG names its fonts. If the playout machine does not have the family, the graphic will not match the design. The import inventories every family and, per family, matches a bundled face, offers the Google Fonts library (fetched at design time and embedded, so exported code never reaches the network), or takes a font file you upload for a licensed face. An unresolved family warns and continues. PostScript names (Archivo-Bold) are understood.

Export settings, app by app

AppSettings that matter
IllustratorFile → Export → Export As… → SVG (not "Save As"). Font: SVG (not outlines) · Images: Embed · Object IDs: Layer Names · Minify: off. Name your layers first; duplicates are safe.
FigmaName the layers, select the frame, Export → SVG with Include "id" attribute ON and Outline text OFF.
InkscapeSave As… → Plain SVG. Label layers and objects. Do not run Object to Path on editable text, and do not use flowed text (drag-drawn text boxes): it exports as <flowRoot>, which no browser renders.

Five files to try are in the repository's docs/svg-samples folder: a lower third, a scorebug, an outlined-text example, an Illustrator-shaped export and a quiz board.

A quiz board can carry its behaviour in the file too. Draw the base look, then one hidden layer per moment (answer picked, right, wrong, locked in). The behaviour pickers on the import's field rows then wire those layers to the quiz events. See graphics with behaviour, and quiz-board.svg in the samples folder.

OBS, vMix & any browser source

A published production gives you one output URL, …/output?production=<slug>, that renders the whole show: transparent, all its graphics, driven live from the playout dashboard. Any source that can load a web page can show it. Load it once and leave it up. Graphics are cued by the operator, not by reloading the source.

Four rules apply to every browser-based playout:

  • The page is already transparent. Do not set a chroma key. A black or white box behind the graphic means the host is forcing an opaque background. Check its custom-CSS and background settings.
  • Match the resolution exactly. Graphics are designed in real pixels (1920×1080 unless you chose otherwise). A mismatch does not crop, it scales, and scaled text is softer than text rendered at its own size.
  • Resize the source, never the resulting layer.
  • Set the source's FPS to the channel's. Motion is authored in seconds and plays correctly at any rate, but a 30 fps source in a 50 Hz channel judders, which is easy to mistake for a fault in the graphic.

OBS Studio

  1. Sources → + → Browser.
  2. Paste the production's output URL. For an exported overlay, unzip the export first, then tick Local file and pick <name>.html from inside the unzipped folder.
  3. Set Width and Height to the graphic's own resolution, and FPS to your channel's.
  4. Leave the background alone.

Leave "Shutdown source when not visible" off for a production output. It tears the page down every time you hide the scene, and forces a full rebuild on the way back.

An exported overlay package ships a local relay and launcher (Start controller.cmd on Windows, start-controller.command on macOS, ./start-controller.sh on Linux). It serves the folder locally, opens the operator page, and relays every command into the graphic, which is the route into a page loaded by OBS's or vMix's own browser engine. It needs no network and no installation.

vMix

  1. Add Input → More → Web Browser.
  2. URL: the output URL, or the full local path to an exported file.
  3. Set the width and height to the graphic's resolution.
  4. Use it as an overlay channel input.

CasparCG

CasparCG plays web pages through its HTML producer, so both routes work: the live output URL for a whole production, or an exported single-file template played from disk with no network at all.

Playing the production's output URL

CG 1-20 ADD 1 "https://noacg.studio/output?production=<slug>" 1
  • 1-20 is channel 1, layer 20. Use whatever your rundown expects.
  • The URL is a capability: anyone holding it can render the production, though not operate it. Treat it like a password.
  • Load it once at the start and leave it up. Graphics are cued from the dashboard, not by re-adding the layer.
  • Add &debug=1 while setting up for an on-screen status readout, and take it off before air.
  • The page recovers by itself after a network drop or a layer restart, rebuilding what was on air without replaying animations.

Every export screen carries a Playout compatibility section measured from the graphic's own code: one line per system saying whether it renders as designed there, and which CSS declaration needs what version.

Letting NoaCG load the layer for you

Instead of typing the command into the CasparCG Client, the production page can send it. Settings → Playout holds one server for the whole studio (host, AMCP port, channel, layer), and the production page grows a Put on air / Take off row. One thing has to run on the machine you operate from, because a browser cannot open a raw TCP socket and AMCP is one: 

npx @noacg/cli caspar agent

Leave that terminal open. It prints an address and token to paste into the Playout settings, listens on 127.0.0.1 only, and CasparCG itself can be any machine on the studio LAN, exactly as with the Client. Test connection round-trips a real AMCP VERSION and shows the server's own version string. On the hosted studio, Chrome asks once whether the site may reach your local network; answer the prompt and it sticks. Safari is expected to refuse this outright, with nothing to grant, though that has not been tested here. Either way the terminal route works: 

npx @noacg/cli caspar play --url "https://noacg.studio/output?production=<slug>" --channel 1 --layer 20

What has been verified The output URL route has run on real hardware: a CasparCG 2.3.2 server rendered it at 1920×1080, transparent, surviving a renderer restart. The one-button connection is newer. Its AMCP wire and every failure state are verified against protocol-accurate fakes and the test suite, but it has not yet driven a real CasparCG server. If it misbehaves on yours, the manual command above is the same live link, and we would like to hear about it.

Playing an exported file

Export with the CasparCG target and you get one self-contained .html, with fonts and images inlined and no network needed. Put it in the server's template folder, which is the template-path set in casparcg.config, and drive it as a normal HTML template. <template-name> below is the filename without its .html extension, relative to that folder: 

CG 1-20 ADD 1 "<template-name>" 1 "<templateData>…</templateData>"
CG 1-20 PLAY
CG 1-20 NEXT
CG 1-20 STOP

A CasparCG client sends values by field id (f0, f1, …), so every exported package ships FIELDS.md: each field's id, name, type and default, with paste-ready payloads built from that graphic's own ids. Keep it open beside the client.

The playout dashboard

A production is the live unit: a pool of graphics, a cue rundown prepared in advance, and one persistent output URL. Each graphic is its own layer, so a bug, a lower third and a ticker can be on air at once.

Making one

  1. In your library, press + Production on a graphic's row. The menu lists the productions you already have, and has a New production… field at the bottom. Naming a new one creates it and puts that graphic in it.
  2. Add the show's other graphics the same way.
  3. Build the rundown on the production page. A cue is a graphic plus the values it airs with.
  4. Press Publish. That mints the output URL a browser source loads, and a control page URL for operating from another device. Publishing needs an account, because the hosted pages live in your cloud space. Everything before it works offline.

The production page's header reads NOT PUBLISHED until you publish and SHOW afterwards. Changes made after publishing reach the output on the next publish.

Running it

  • Preview and program. Two monitors and the verbs an operator uses: select a cue, check it on preview, Take. Selecting and previewing never reach air; Take is what airs. Staged edits air on an explicit take, never mid-keystroke.
  • Drive it from any browser, including an OBS dock or a phone at the desk.
  • Recovery. Every command is a row in a durable log. The on-air renderer applies rows in order and, after a network drop or restart, catches up in order, rebuilding what was on air without replaying animations on screen.
  • Pictures without templates. "＋ Add pictures…" turns image files into cues, such as a holding slide or a sponsor card, aired like any other cue. There is one picture layer per production, so stills replace rather than stack.

Audience join pages

A production can invite its audience in. A public join page at a readable URL (noacg.studio/join/<name>, the kind you read out on air) collects viewer messages and votes from any phone, with no app and no account.

  • Nothing viewer-written airs on its own. Send-ins land in a moderation inbox, and an operator picks what goes into the graphic. There is no setting that airs a send-in automatically.
  • Votes tally live into poll graphics. Open the vote, close it, put the result on air when you are ready.
  • A presenter view (a separate link) shows the host what is coming without giving them operator controls.

Graphics with behaviour

A lower third plays and stops. A quiz board has to know which answer the contestant locked in and whether it has been revealed yet. NoaCG graphics can carry that logic themselves, as named states and real operator events. The control panel is generated from them, so a move the current state does not allow is greyed out.

  • A quiz runs Select answer, Lock it in, Reveal. Each one is a button on the dashboard, and each is legal only when the board's state allows it.
  • A scoreboard carries score up/down and clock start/stop as events. The numbers are data an operator or a feed writes.
  • Data never causes a state change. Updating a name or a score re-renders fields. States move only on operator events, so a feed can be left running.
  • Everything still degrades to plain stepping. Hand the same graphic to any playout system and it walks its steps in order like an ordinary template. The extra buttons appear when NoaCG drives it.

You can author behaviour without code. An imported SVG quiz board is layers: draw each moment (answer picked, right, wrong, locked in), hide those layers in the design app, and the import wires them to the quiz behaviour. See the SVG guide.

Live data

Three ways to get data in, from no setup to fully automated. All of them follow the same rule: data updates change what a graphic shows, never what state it is in. An operator's command lands later in the same log than a feed's, so it applies last.

Type it on the dashboard

Every field is editable live from the production page: edit, stage, take. For most shows nothing else is needed.

A Google Sheet (or any published CSV)

Point a graphic at a published sheet and its fields follow the sheet. Anyone with edit access to the sheet can change them. In the sheet: File → Share → Publish to web → CSV. In the studio, add the live-data source and paste the link. The generated polling code is ordinary, commented JavaScript appended to the graphic's own code, with column headers mapped to field titles. It runs wherever the graphic runs: the preview, an OBS browser source, an exported package. The mapping is editable like the rest of the code.

The Production Data API

For a timing system, a results service or your own scripts: push values into a published production over plain HTTPS, authenticated by the production's own data key. Writes become rows in the production's command log, so the renderer cannot tell your update from an operator's.

Where to find the key. Publish the production, open its Data tab, and press ▾ Data key in the Production data panel. Reveal it, copy it, and put it in your integration's server-side configuration. Publishing again mints a new key and the old one stops working, which is also how you revoke one. 

curl -s https://noacg.studio/api/data/update \
  -H "Authorization: Bearer $NOACG_DATA_KEY" \
  -H "Content-Type: application/json" \
  -d '{"graphic": "House Scorebug", "values": {"Score A": 2, "Clock": "43:12"}}'
  • Fields are addressed by the labels the graphic shows its operator ("Score A").
  • The key writes data and reads the production's current data back. It cannot play, stop, take or clear anything. Cueing and clearing stay with the operator.
  • /api/data/patch (PATCH, or POST behind a proxy that eats PATCH) writes to a data path such as match.home.score instead of to a named graphic. Every graphic whose field is bound to that path follows, so the feed does not have to know the rundown. The binding is set up in the studio first.
  • A worked example ships in the repository: a weather mini-pack driven by a small Node connector polling Open-Meteo. The full reference, limits and error shapes are in DATA_API.md.

Make graphics with Claude Code, Codex or any coding agent

A coding agent can create the HTML, CSS and JavaScript for a graphic. NoaCG turns that graphic into something you can actually use on air: with operator controls, live events, validation and predictable playout behaviour. The NoaCG CLI gives coding agents everything they need to build to that standard. It carries the NoaCG contract, runs the same validator as the Studio, and can add the finished graphic directly to your library.

What lands there is an ordinary NoaCG graphic: it goes into a production, answers the operator events its own behaviour defines, and takes live data from a sheet or an API.

Connect NoaCG to your agent

Two commands, once per machine. After that you talk to your agent, not to the CLI.

Claude Code. The plugin carries the noacg-graphic skill, a /noacg:graphic command and the tools, with nothing to install first. 

claude plugin marketplace add miwco/NoaCG-Studio
claude plugin install noacg@noacg-studio

Codex. The same plugin, from the same repository.

codex plugin marketplace add miwco/NoaCG-Studio
codex plugin add noacg@noacg-studio

Any other agent that speaks MCP. Register the server over stdio: command npx, arguments -y @noacg/cli mcp. It brings the tools, and the contract text comes with them as the server's own resources. 

npx -y @noacg/cli mcp

All three need Node.js 20 or newer and a system Chrome or Edge, which the validator drives in headless mode. No account is needed until you save a graphic into a library.

Then describe the graphic you want

"Make me a clean scoreboard for a floorball stream: home, away, period, clock." In Claude Code, /noacg:graphic starts the same thing.

The part that makes that work is the noacg-graphic skill the plugin carries. It teaches the agent how a NoaCG graphic is put together, which tools to reach for, how to validate what it wrote, and how to save the result into your library. It says nothing about how the graphic should look, which stays the agent's job.

Working from that, the agent:

  1. Scaffolds a starting package when the graphic needs a type's fields and operator events. This step is optional: it can also author from scratch against the contract.
  2. Authors the graphic itself, the way it normally writes code.
  3. Validates it against the studio's own gate and a live playout bench, with off-air, on-air and stress screenshots, so it can see what it made.
  4. Iterates on the findings, which read the way a compiler reports errors, until they are clean.
  5. Saves it into your NoaCG library and prints the link.

Saving is the one step that needs you. Run noacg login once per machine and approve it in the browser. The key it stores can only create graphics in your library, and Settings, under Account, Agent access, revokes it. 

npx @noacg/cli login

save refuses a graphic that does not pass validation. What it saves is editable in the studio like any other graphic, and exports to every target NoaCG supports.

Reference

All three entrances above are one npm package, @noacg/cli, installing one command, noacg. You can also run it yourself. 

npm i -g @noacg/cli

Every command also works as npx @noacg/cli <command> with nothing installed. The loop by hand is three of them: 

npx @noacg/cli scaffold --type scoreboard --design neutral --out my-scorebug
npx @noacg/cli validate my-scorebug --screenshots shots
npx @noacg/cli save my-scorebug

scaffold creates the directory relative to where you run the command, and it has to be new or empty. noacg types lists the graphic types the deployment knows, with their fields and operator events, which is where a --type value comes from.

The MCP server without the skill. For the tools in Claude Code but not the plugin: 

claude mcp add noacg -- npx -y @noacg/cli mcp

That registers it for the directory you run it in; add --scope user to have it everywhere. The server exposes types, scaffold, validate, inspect, screenshot, save and the contract references, so an agent can read the contract through noacg_docs before it has a deployment or a key.

Which files to edit. A package holds sources and generated files. Edit <name>.html, css/template.css, js/template.js, and the images/ and fonts/ folders. Leave <name>.ograf.json, graphic.mjs, FIELDS.md, README.md and controlpanel.html alone: validate rewrites them from the sources, so an edit made there is lost.

Which deployment it talks to. https://noacg.studio by default. NOACG_URL points it at a local dev server or a self-hosted one instead. NOACG_BROWSER names a Chromium executable when the system Chrome or Edge is not the one to use, and NOACG_AGENT_KEY supplies a key in CI, where nothing can open a consent page in a browser.

When something fails for a reason the findings do not explain, doctor prints what the tool resolved: which browser it will drive, which deployment NOACG_URL points at, the bridge version it found there, and whether a key is held. 

npx @noacg/cli doctor

What the package is. The folder is at the same time a valid SPX package and an EBU OGraf v1 graphic. Zip it and it also imports through the studio's Import door, or plays in any OGraf renderer. Those two are what the folder satisfies with no build step; the graphic itself is plain HTML, CSS and JavaScript, so the same sources also export to CasparCG, an OBS or vMix overlay, H2R and LiveOS. The full reference is AGENT_CLI.md.
